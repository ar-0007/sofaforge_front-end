# Deployment — Render (API) + Netlify (site)

Two deployables, one repo:

| What | Where | Built from | Config |
|---|---|---|---|
| `backend/` — Express + tRPC API | Render Web Service | repo root (pnpm workspace) | `render.yaml`, `backend/.env.production.example` |
| `frontend/` — Next.js 15 site | Netlify | repo root (pnpm workspace) | `netlify.toml`, `frontend/.env.production.example` |
| `shared/` — types + constants | **nothing to deploy** | bundled into both builds at compile time | — |
| MySQL database | external host (Render has no MySQL) | — | `DATABASE_URL` |
| `backend/uploads/` — admin photos | Render Disk at `/var/data` | — | `UPLOAD_DIR` |
| `docs/`, `references/` | **nothing to deploy** | notes only | — |

`shared/` is *not* a published package. esbuild inlines it into `backend/dist/server.js`
and Next compiles it via `externalDir`. It only has to be present in the repo when
each build runs — which is why both builds run from the repo root, not from the
app subdirectory.

---

## 0. The database — pick this first

The schema is MySQL (`drizzle-orm/mysql2`, 6 tables, **no foreign keys**).
Render only offers PostgreSQL, so the database has to be hosted somewhere else.

Recommended, in order:

1. **Aiven for MySQL — free plan.** Real MySQL 8, 1 GB, TLS, no credit card.
   The right choice for a client review build. Pick a region near the Render
   region so latency stays sane.
2. **Railway MySQL** — trivially easy, ~$5/mo of credit, good if the free tier
   runs out of room.
3. **Your Hostinger VPS** — you already need one for other reasons; MySQL is
   already there. Just open port 3306 to Render's egress and force TLS.

PlanetScale is *technically* fine (the schema has no foreign keys, which is its
usual blocker) but it no longer has a free tier, so it buys nothing here.

Managed providers require TLS. The connection string then looks like:

```
mysql://USER:PASSWORD@HOST:PORT/DBNAME?ssl={"rejectUnauthorized":true}
```

Create an empty database — the migrations build every table.

## 1. Backend on Render

1. Push this branch to GitHub.
2. Render → **New → Blueprint** → select the repo. It reads `render.yaml`,
   creates `sofaforge-api`, and prompts for the `sync: false` variables:
   `DATABASE_URL`, `CORS_ORIGIN`, `DEV_ADMIN_EMAIL`, `DEV_ADMIN_PASSWORD`.
   `JWT_SECRET` is generated by Render and kept across deploys.
3. `CORS_ORIGIN` is not known yet — put `https://placeholder.netlify.app` and
   correct it after step 2. No trailing slash.
4. Deploy. The build runs migrations then bundles:
   ```
   corepack enable
   pnpm install --frozen-lockfile --prod=false
   pnpm --filter @sofa/backend db:migrate
   pnpm --filter @sofa/backend build
   ```
5. Verify: `curl https://sofaforge-api.onrender.com/api/health` → `{"ok":true}`.

### Things that will bite you

- **`--prod=false` is load-bearing.** pnpm skips `devDependencies` whenever
  `NODE_ENV=production`, and esbuild, drizzle-kit and tsx all live there.
  Drop the flag and the build fails with "esbuild: not found".
- **Never set `PORT` or `API_PORT` on Render.** Render injects `PORT`. An
  `API_PORT` you set by hand wins over it and the health check never passes.
- **The disk is not optional if the client will upload photos.** Admin images
  are written to `UPLOAD_DIR` on local disk. Without the Render Disk mounted at
  `/var/data`, every deploy and every restart wipes them. Disks need a paid
  plan — they are unavailable on `free`.
- **Free plan sleeps.** A free service idles out after 15 minutes and the next
  request waits ~50s for a cold start. Fine for a demo you warn the client
  about; annoying if they are clicking around unprompted.
- `[OAuth] ERROR: OAUTH_SERVER_URL is not configured` in the logs is expected
  and harmless — Manus OAuth is unused, admin login goes through the
  email+password route.

## 2. Frontend on Netlify

1. Netlify → **Add new site → Import from Git** → same repo. It picks up
   `netlify.toml`, so leave the build settings alone.
2. Set the environment variables from `frontend/.env.production.example`.
   The one that matters: `API_PROXY_TARGET=https://sofaforge-api.onrender.com`.
3. Deploy, then note the real site URL.
4. **Go back to Render and set `CORS_ORIGIN` to that URL.** Save — Render
   redeploys.

### Why `NEXT_PUBLIC_API_URL` stays empty

`frontend/next.config.ts` rewrites `/api/*` to `API_PROXY_TARGET`. The browser
therefore only ever calls its own origin, the session cookie stays **first-party**,
and none of the third-party-cookie rules apply. Point `NEXT_PUBLIC_API_URL` at
Render directly and every API call becomes cross-site — which then works or
doesn't depending on the client's browser settings. Don't.

## 3. Admin access for the client

Manus OAuth is not configured, so `/admin` is reached through the email+password
route in `backend/src/modules/auth/devAuth.ts`. It is **off by default** in
production; `render.yaml` switches it on with `ALLOW_DEV_LOGIN=true`.

That route compares against two plaintext env vars and has no rate limiting.
It is adequate for a review build behind a URL nobody else knows, and it is
**not** adequate once the shop takes real orders. Give it a long random
password now, and replace it before launch (ARCHITECTURE.md §8).

## 4. Post-deploy checklist

```bash
API=https://sofaforge-api.onrender.com
SITE=https://your-site.netlify.app

curl -s $API/api/health                      # {"ok":true}
curl -s $API/api/auth/dev-login              # {"enabled":true,"email":"..."}
curl -s -D - -o /dev/null -X OPTIONS \
     -H "Origin: $SITE" $API/api/trpc \
  | grep -i access-control-allow-origin      # must echo $SITE back
```

Then in a browser: open `$SITE`, log in at `/admin`, upload one product photo,
and **redeploy the Render service** — if the photo survives, the disk is
mounted correctly. If it 404s, `UPLOAD_DIR` is not on the disk.

## 5. Seeding the catalogue

The migrations create empty tables. To load products:

```bash
pnpm --filter @sofa/backend db:seed       # baseline rows
pnpm --filter @sofa/backend db:catalog    # WooCommerce catalogue import
pnpm --filter @sofa/backend db:options    # configurator option groups
```

Run these locally with `DATABASE_URL` pointed at the *production* database —
they are one-off imports, not part of the deploy.
